SKIP LOCKED 문제 8.0 이전 세 잠금 의미론 사례 함정 정리
0 문제 ~1분

FOR UPDATE SKIP LOCKED
기다리지 말고, 건너뛰어라

MySQL 8.0이 들여온 잠금 옵션 한 줄. 왜 도입됐고, 기존 잠금과 무엇이 다른가 — 그리고 그게 왜 "풀에서 하나 선점하기" 문제를 통째로 바꿨는가.

MySQL 8.0.1+ (2017) 작업 큐 · 재고 예약 풀 · outbox 동시성 패턴
오늘의 한 장면: 워커(혹은 결제 요청) 여러 개가 한 테이블에서 "아직 아무도 선점하지 않은 행 하나"를 동시에 가져가야 한다 — 작업 큐, 재고 예약 풀, outbox 릴레이. 순진하게 FOR UPDATE로 짜면? 전부 같은 행 앞에 줄을 선다.
1 배경 ~3분

8.0 이전엔, '하나 선점'이 왜 아팠나

워커 N개가 동시에 "ready인 행 하나"를 선점하려 한다:

-- 모든 워커가 똑같이 '가장 앞 행'을 노린다
SELECT id FROM jobs WHERE status='ready'
ORDER BY id LIMIT 1 FOR UPDATE;   -- 8.0 이전: 옵션 없음

한 놈이 그 행을 잠그면, 나머지는 같은 행이 풀릴 때까지 대기한다 (최대 innodb_lock_wait_timeout, 기본 50초 → 에러 1205). 워커를 아무리 늘려도 유효 동시성은 사실상 1. 그래서 다들 우회했다 — 셋 다 나름의 대가가 있었다.

① status 컬럼 플립

SELECT로 ready 하나 찾고 → UPDATE status='taken'. 그 사이 다른 워커가 같은 행을 가로채 이중 처리, 또는 트랜잭션으로 막으면 다시 경합.

② 어드바이저리 락 (GET_LOCK)

앱이 키를 정해 분산 잠금. 키 설계 부담 + 커넥션에 묶임 + 자동 해제·세션 종료 함정. 결국 잠금 로직이 앱으로 샌다.

③ 외부 큐 (Redis/SQS)

잘 된다. 단 또 다른 시스템 — 운영·정합성·"진실이 두 곳" 문제를 새로 안는다. (Shopify가 겪던 바로 그 분리 구조.)

공통 고통: 남이 잡은 행을 "기다리느라" 처리량이 안 나오거나, 안 기다리려고 앱·외부 시스템으로 우회하다 복잡도가 샌다.
2 핵심 — 세 가지 잠금 동작 ~5분

FOR UPDATE vs NOWAIT vs SKIP LOCKED

8.0.1부터 FOR UPDATE에 두 옵션이 붙었다. 핵심은 "잠긴 행을 만났을 때 무엇을 하느냐" 하나로 갈린다.

셋의 차이는 "잠긴 행을 만났을 때" 하나: 대기 / 즉시 실패 / 건너뛰기.
옵션잠긴 행을 만나면실패 코드용도
FOR UPDATE풀릴 때까지 대기1205(timeout)반드시 그 행을 처리해야 할 때
… NOWAIT즉시 에러3572대기 대신 빠르게 실패·재시도
… SKIP LOCKED건너뛰고 다음—풀에서 아무거나 하나 선점
 
-- "지금 잠글 수 있는 행 하나만 즉시 가져온다" — 큐/풀의 정석
SELECT id FROM jobs WHERE status='ready'
ORDER BY id LIMIT 1 FOR UPDATE SKIP LOCKED;
3 의미론 — 공짜가 아니다 ~3분

SKIP LOCKED는 '일관된 읽기'가 아니다

건너뛴다는 건 곧 "다른 트랜잭션이 잠근 행을 결과에서 누락한다"는 뜻이다. 두 워커가 같은 쿼리를 동시에 돌리면 서로 겹치지 않는 행을 받는다 — 그게 목적(작업 분배). 하지만 같은 이유로, "지금 ready인 행이 몇 개냐"를 정확히 셀 수는 없다(잠긴 건 안 보이니까).

✓ 잘 맞는 곳

작업 큐 워커 · 재고 예약 풀에서 하나 선점 · outbox/이벤트 릴레이 · rate-limited claim — 공통점: "아무거나 잠글 수 있는 거 하나면 된다".

✗ 쓰면 안 되는 곳

정확한 집계 · 잔액 · 남은 수량 정확히 세기 · 리포트 — 일관 스냅샷이 필요한 읽기. 잠긴 행을 빼고 세므로 수가 틀린다.

"재고 예약에 썼는데 왜 ✗?" — 모순이 아니다. 갈림은 도메인이 아니라 동작이다. SKIP LOCKED로 한 건 "빈 단위 하나 선점(claim)" — 잠긴 행은 건너뛰고 안 잠긴 행 하나를 가져오는 할당이다. 반대로 "남은 수량을 정확히 세기(count)"에 쓰면 진행 중인 예약이 잠근 행이 빠져 수가 틀린다. 같은 재고 도메인이라도 선점엔 ✓, 세기엔 ✗.
역사: SKIP LOCKED·NOWAIT는 MySQL 8.0.1(2017)에 추가됐다. PostgreSQL은 9.5(2016), Oracle은 훨씬 전부터 있었다 — MySQL이 늦은 편이라, 그 전까지 다들 §1의 우회책을 썼던 것.
한 줄: 건너뛴다 = "본다"는 보장을 포기한다. 작업 분배엔 축복, 정확 집계엔 독.
4 사례 — Shopify, 그리고 우리 PoC ~4분

재고 예약을 'SKIP LOCKED 풀'로

Shopify는 재고를 quantity 한 칸이 아니라 판매 단위마다 1행(one-row-per-unit)으로 펼치고, 예약을 "풀에서 행 하나 선점"으로 바꿨다. 핫 아이템에 수백 명이 몰려도 SKIP LOCKED가 서로 다른 행을 집게 해 락 경합 자체를 없앤다.

"하나의 핫 행"을 "N개 단위 행"으로 펼치고, 잠긴 건 SKIP LOCKED로 건너뛰니 동시 예약이 충돌하지 않는다.

우리 PoC로 직접 확인

1개 핫 아이템(HOT_SINGLE)에 clients=200을 몰아넣고 mysql-skip-locked 전략으로 실측:

0
oversell (정합성 깨짐)
true
conserved (재고 보존)
2,194
req/s (대기 없이 완주)

핫 아이템 한 곳에 200명이 동시에 몰려도 초과 판매 0 — 행 하나씩 선점하니 서로 충돌하지 않는다. (Redis와의 처리량 비교·커넥션 병목 등은 이 발표 범위 밖. 레포의 3-way 결과 문서 참고.)

5 함정 — 잠금 고민의 끝이 아니다 ~3분

SKIP LOCKED를 써도 gap lock·격리수준은 남는다

SKIP LOCKED는 잠긴 레코드를 건너뛸 뿐, 그 아래 InnoDB의 gap lock과 격리수준 규칙까지 없애주진 않는다. 잠금-읽기(FOR UPDATE)가 비어 있거나 소진된 인덱스 범위를 스캔하면 끝(supremum 의사 레코드)까지 가며 gap lock을 잡고, 그 빈 범위에 INSERT가 겹치면 — REPEATABLE READ에선 두 트랜잭션의 gap lock + insert-intention이 순환 대기 → 데드락이 된다.

이게 실제로 어디서 터지나: 재고 예약은 전 재고를 행으로 만들지 않고 일부만(예: 1,000행) '풀'로 두고 모자라면 원장에서 행을 채워 넣는다(replenishment INSERT). 그 풀이 비어 보충 INSERT가 도는 순간이 바로 위 상황 — "빈 범위 + INSERT"다.

READ COMMITTED는 gap lock을 안 잡아 두 INSERT가 모두 통과한다 — Shopify가 기본 격리수준을 RR→RC로 바꾼 이유.
isolationdeadlocks(1213)성공비고
REPEATABLE READ20 / 2020매 라운드 데드락
READ COMMITTED040깨끗

우리 PoC 실측 — 빈 테이블 + plain FOR UPDATE로 전 범위 스캔을 강제하고 배리어로 두 트랜잭션을 맞붙인 최소 데모. 정직한 반전: 정작 SKIP LOCKED를 쓴 자연 경로에선 데드락이 잘 안 났다 — SKIP LOCKED가 빈 행을 일찍 선점하고 멈춰 supremum까지 안 가기 때문. 즉 SKIP LOCKED는 이 함정을 오히려 완화하지만, 격리수준이 RR이면 빈 범위 INSERT에서 여전히 걸릴 수 있어 격리수준을 함께 봐야 한다는 게 요점.

교훈: SKIP LOCKED는 "대기"를 없애주지만, 격리수준·gap lock과의 상호작용까지 없애주진 않는다. 잠금은 항상 격리수준과 함께 봐야 한다.
6 정리 ~1분

가져갈 것 세 가지

① 기다리지 말고 건너뛰어라

"풀에서 하나 집기"는 SKIP LOCKED가 정답. status 플립·advisory·외부 큐 같은 8.0 이전 우회책을 DB 한 줄로 대체한다.

② 단, 일관 읽기가 아니다

잠긴 행을 누락한다. 작업 분배엔 축복, 정확 집계엔 독 — 쓰기 전에 "이건 분배인가 집계인가"를 먼저 묻자.

③ 잠금은 격리수준과 함께

SKIP LOCKED 위에서도 gap lock·RR/RC가 다시 발목을 잡는다. 우리 실측 RR 20 vs RC 0 — 옵션 하나로 끝나는 게 아니다.

더 깊게: 재고 예약: 정합성과 처리량은 맞바꾼다 — 같은 PoC를 3-way 비교(MySQL·Redis·분리)와 커넥션 병목까지 다룬 종합본 · 영감: Shopify — Scaling Inventory Reservations
