재고 예약:
정합성과 처리량은 맞바꾼다

체크아웃에서 "재고를 잡는다(reserve)"는 단순해 보이지만, 양방향으로 동시에 틀리면 안 된다. Shopify의 Scaling Inventory Reservations를 로컬에서 직접 재현·측정한 PoC 이야기.

① Oversell — 초과 판매

마지막 1개를 두 명이 동시에 산다. 결제는 됐는데 줄 물건이 없다. → CS·환불·신뢰 붕괴.

② Undersell — 헛품절

재고가 있는데 "품절"로 막는다. → 팔 수 있었던 매출을 그냥 버린다.

한쪽으로 틀리면 두 명이 같은 마지막 하나를 사고, 반대로 틀리면 있는데도 품절이라 말한다. 피크에는 분당 $5.1M가 흐르는 경로(Shopify 2025 BFCM) — 이 줄타기를 어떻게 할 것인가.

Kotlin · Spring Boot 3.4 MySQL 8.0 · Redis 6 코루틴 부하 하니스 로컬 단일 머신 · 상대 비교
1 배경 & As-Is → To-Be ~2분

왜 이렇게 바꿨나 — 분리된 진실을 하나로

예전엔 왜 둘로 나뉘었을까요? 예약은 결제 트래픽을 받아내는 빠른 원자 카운터가 필요해 Redis에 뒀고 (원문: 아이템당 quantity 키, 예약=DECR·해제=INCR), 재고 원장은 영구적 진실·정산이라 MySQL에 뒀습니다. 각자는 합리적이었어요. 문제는 claim(결제 확정): Redis 예약 해제 + MySQL 원장 차감을 하나로 묶어야 하는데, 서로 다른 시스템이라 이기종 트랜잭션을 묶을 수 없습니다. 둘의 커밋이 어긋나면 over/undersell. → 해법은 단순합니다: 예약을 MySQL로 들여와 원장과 한 트랜잭션에. 단, 그 대가로 생기는 락 경합·확장성 문제를 아래 '설계 3가지'로 풉니다. (구현하다 부딪힌 InnoDB 저수준 문제 3가지는 뒤 '구현 디테일' 섹션에서 — 원문도 '설계'와 'InnoDB 이슈'를 분리해 다룹니다.)

핵심 차이: "진실이 두 시스템에 쪼개져 원자적으로 못 묶이던 것"(AS-IS)을 "예약+원장을 MySQL 한 트랜잭션으로"(TO-BE) 합친 것. 그 합치기의 *대가*(락 경합·gap lock·데드락)를 갚는 게 설계 3가지 + 뒤 '구현 디테일' 3가지다.

TO-BE를 이루는 설계 3가지 — 어떻게 동작하나

아래 3가지가 곧 위 To-Be 박스의 내용. (합치기의 *대가*를 갚는 InnoDB 디테일 3가지는 뒤 '구현 디테일' 섹션에서.)

→ one-row-per-unit

한 행에 몰리던 락 경합을 N개 행으로 분산해 동시에 다른 행을 잡게.

→ FOR UPDATE SKIP LOCKED

잠긴 행은 기다리지 않고 건너뛰어 다음 빈 행을 잡음(비대기).

→ bounded pool + replenishment

전 재고를 행으로 안 만들고 1000행만; 줄면 원장에서 되채움. (이 보충 INSERT가 뒤 '구현 디테일'의 READ COMMITTED 문제의 원인.)

2 3-way 셋업 ~2분

같은 부하로 세 가지 방식을 비교

Shopify의 답(TO-BE = ① MySQL)을 그냥 믿지 말고, 직접 ②③와 재현·측정해 확인해보자. 동일한 시나리오·부하 생성기·정합성 오라클로 세 전략을 돌려, 차이가 전략에서만 나오게 했다.
※ 헷갈리지 말 것: 앞 '설계 3가지'(one-row·SKIP LOCKED·bounded pool)는 모두 ① 안의 구성요소다. 여기 ①②③는 그 ①과 견줄 다른 전략(비교 대상).

① MySQL SKIP LOCKED

재고 1개 = row 1개(one-row-per-unit). 트랜잭션이 행을 원자적으로 잠근다.

② 순수 Redis

재고를 카운터 하나로. Lua로 검사+차감을 한 번에(원자).

③ Redis + MySQL 분리

예약 카운트는 Redis, 판매 원장은 MySQL. 두 스토어가 따로 논다.

① 핵심: FOR UPDATE SKIP LOCKED

-- 잠긴 행은 '기다리지 않고' 건너뛴다 → 핫 아이템 경합 제거 (MySQL 8.0+)
SELECT id FROM reservation_units
WHERE shop_id=? AND item_id=? AND location_id=?
LIMIT ? FOR UPDATE SKIP LOCKED;
-- 잡은 행을 DELETE → reserved_quantities로 INSERT (한 트랜잭션, READ COMMITTED)

② 핵심: Redis 원자 차감 (Lua)

local stock = tonumber(redis.call('GET', KEYS[1]))
if stock == nil or stock < qty then return 0 end
redis.call('DECRBY', KEYS[1], qty)   -- 검사와 차감이 한 번에 (TOCTOU 없음)
redis.call('HSET', KEYS[2], rid, qty)
return 1

③ 핵심: 검사와 행위가 두 스토어에 흩어진 check-then-act

sold     = SELECT sold FROM inventory_ledger      // MySQL 읽기
reserved = GET reserved:{item}                   // Redis 읽기
if (total - sold - reserved >= qty) {           // 검사(CHECK)
   INCRBY reserved:{item}                       // 행위(ACT) — 락 없음, 그 사이 누가 끼어듦
}

세 방식 모두 reserve → claim(결제확정) → release(취소) 라이프사이클과 정합성 오라클 (sold + reserved + available == total, oversell 수)로 검증.

CHECK(읽기)와 ACT(증가)가 원자가 아니고 두 스토어에 흩어져 있어, 그 사이 창(붉은 영역)에서 둘 다 "남았다"고 판단한다.
재고가 막판(10개)일 때 oversell 40건. 재고가 충분한 HOT_SINGLE/MIXED에서는 안 터진다 — 정확히 가장 중요한 순간(품절 직전)에만 깨진다.
오독 주의: ②(순수 Redis)의 oversell 0은 "Redis가 더 안전"이 아니다. 단일 스토어라 원자성이 유지될 뿐이고, 문제는 ③처럼 원장이 분리될 때 생긴다. (Redis만 쓰면 영속성·장애 시 재고 소실이라는 다른 리스크가 따로 있다.)
트레이드오프 한 줄: 처리량 ② ≫ ③ > ① · 정합성은 ①·②가 안전하고 ③가 위험. → “빠르다”가 아니라 “원자 경계가 하나인가”로 골라야 한다.

슬라이더를 움직여 보세요 — 풀이 커질수록 대기 큐가 줄고 처리량이 회복된다.
"The query is fast; it's the wait for a connection that kills you."

Shopify의 진짜 발견도 이거였다 — 쿼리·락은 몇 주를 깎았지만(composite PK·격리수준 등 저수준 튜닝, 뒤 '구현 디테일'), 정작 천장은 예약 쿼리가 아니라 체크아웃 경로의 다른 코드가 — 자기들이 보지도 않던 코드가 — 커넥션을 오래 물고 있던 것. per-caller로 커넥션 점유를 계측해 찾아냈고, 정리 후 primary read 50%·트랜잭션 33% 감소.

교훈: 내 쿼리만 빠르면 되는 게 아니다. 공유 자원(커넥션 풀)의 “좋은 이웃(safe neighbor)”이 되어야 한다. 느린 건 종종 쿼리가 아니라 대기다 — 그래서 전체 경로를 계측해야 한다.
5 구현 디테일 — InnoDB 심화 · skip 가능 ~3분

설계를 실제로 굴리며 부딪힌 저수준 문제 3가지

앞의 설계(one-row · SKIP LOCKED · bounded pool)를 MySQL에서 돌리다 만난 InnoDB 레벨 이슈들 — Shopify 글도 'the new design'과 별개로 "we hit and fixed"로 따로 다룬다. (① MySQL 전략에만 해당)

→ composite PK

보조 인덱스로 행을 찾으면 InnoDB가 보조 레코드 + 클러스터드(PK) 레코드를 둘 다 잠근다(2잠금) → 조회 컬럼을 복합 PK 앞자리에 두면 클러스터드에서 바로 찾아 row당 1잠금.

→ READ COMMITTED

RR은 gap lock으로 빈틈을 잠가 INSERT를 막음; RC는 안 잡아 통과.

→ lock ordering 고정

반대 순서로 잠그면 순환 대기; 순서를 고정(units 먼저)해 제거.

※ 원문엔 멀티아이템 카트의 라운드트립을 줄이는 batching(UNION ALL)도 4번째 결정으로 나오지만, 우리 PoC는 단일 아이템 부하만 다뤄 범위 밖(미구현)이라 카드로 넣지 않았다.

특히 READ COMMITTED는 앞 bounded pool의 replenishment INSERT가 gap lock에 막히던 문제를 푼 것 — 바로 다음 섹션에서 실제로 재현한다.
6 심화 — gap-lock 데드락 (RC를 실측으로) skip 가능 ~3분

왜 REPEATABLE READ를 버리고 READ COMMITTED로 갔나

앞 '구현 디테일'의 READ COMMITTED 카드를 실제로 재현한다 — 재고 보충(replenishment)을 붙이면 격리수준이 데드락을 만든다(Shopify가 기본 격리수준을 바꾼 이유).

메커니즘: 빈 인덱스 범위에서 WHERE id>0 FOR UPDATE가 supremum까지 스캔 → 두 트랜잭션이 공유 gap lock을 동시 획득(호환되므로 통과) → 양쪽이 그 gap에 INSERT 시도 → insert-intention이 상대 gap lock과 충돌 → 순환 대기. READ COMMITTED는 gap lock을 안 잡아 둘 다 통과.
정직한 발견: 정작 자연스러운 reserve+replenishment 경로에서는 데드락이 재현되지 않았다(RR·RC 모두 0). SKIP LOCKED는 빈 행을 만나면 일찍 멈춰 supremum까지 안 가고, 못 찾으면 즉시 롤백 → bounded pool 설계가 역설적으로 gap 스캔을 회피한다. 그래서 메커니즘은 배리어로 동기화한 최소 데모로 결정적으로 입증했다.
7 정리 ~1분

가져갈 것 세 가지

① 트레이드오프는 “원자 경계”로

빠른 게 안전한 게 아니다. ②가 제일 빠르지만 위험한 건 ③(분리 구조). 정합성은 원자 경계가 하나인지로 결정된다.

② 병목은 종종 “대기”다

쿼리가 빨라도 커넥션 점유로 막힌다. 공유 자원의 safe neighbor가 되고, 국소 최적화 말고 전체 경로를 계측하라.

③ 오래된 제약은 다시 보자

SKIP LOCKED는 MySQL 8.0+. 5년 전 불가능했던 게 지금은 된다 — Redis로 우회했던 이유가 사라지면 단순화 기회가 생긴다.

+ 방법론

글 하나를 읽고 끝내지 않고 — brainstorm → spec → plan → 구현 → 검증으로 로컬에서 직접 재현·측정했다. "REPEATABLE READ에서 데드락이 안 나더라" 같은 음성 결과도 숫자를 지어내지 않고 정직하게 기록 → 그게 또 다른 발견이 됐다.
